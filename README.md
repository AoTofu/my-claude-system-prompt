# my-claude-system-prompt

Claudeに日本語で事実や手順を書かせるときの、個人用のシステムプロンプトです。本文は [`system-prompt.md`](./system-prompt.md) にあります。

このプロンプトは、読み手が聞き返さずに判断と作業に進める文章を目標にしています。そのために、文の読み方が1つに決まること、事実と推測を分けること、比喩を使わないことを優先します。日本語の文章の好みは人によって大きく違います。このREADMEでは、このプロンプトが出力をどう変えるか、どんな人に向いていてどんな人に向かないかを先に説明します。

## 構成

表1 `system-prompt.md` の3つの節と、それぞれが決める内容

| 節 | 決める内容 |
| --- | --- |
| `<information_density>` | 何をどこまで書くか。最初の1文で答えること、判断を変える項目を省かないこと、事実と推測を分けること、数値の出典の付け方、最後の段落の書き方 |
| `<writing_rules>` | 文をどう書くか。13個の規則で、主語、比喩、太字、括弧、読点、情報の順序、キャプションなどを決める |
| `<final_check>` | 送る前に確かめる項目。確かめた結果は回答に書かせない |

適用範囲は、日本語で判断や作業を求める質問への回答と、ソースコードのコメント、commit message、PR概要欄、ドキュメント、wikiです。雑談、悩みの相談、創作、翻訳には適用しません。

## 出力がどう変わるか

表2 このプロンプトを使ったときと使わないときの、典型的な書き方の違い。右の列はプロンプトが求める書き方の例

| 観点 | よくある書き方 | このプロンプトの書き方 |
| --- | --- | --- |
| 答えの位置 | 前置きや質問の言い換えから始める | 最初の1文で答える |
| 選択を問う質問 | 「状況によります」 | 「条件Xのときは、Aを推奨する。理由はYである」 |
| 比喩 | 「この設定はtimeoutに効く」 | 「この設定を変えるとtimeoutの値が変わる」 |
| 無生物の主語 | 「ログが原因を教えてくれる」 | 「ログを見ると原因が分かる」 |
| 主語の省略 | 「handlerが呼ばれ再描画する」 | 「handlerが呼ばれる。その後Reactが再描画する」 |
| 確かでない事 | 「〜と思われる」 | 「私は〇〇を確認できていない」と書き、確かめる方法も書く |
| 補足 | 丸括弧やダッシュで挟む | 文を分けるか、子リストにする |
| 読点 | 「この関数は、空の配列を、返す。」 | 「この関数は空の配列を返す。」 |
| 太字 | 重要な文を太字にする | 書名、定義する用語、項目名、画面上の名前だけを太字にする |
| 和文と英字 | 「Modal を dialog に」 | 「Modalをdialogに」 |
| 表と図 | 番号や題がない | 「表1 3つのcache方式のヒット率、単位は%」のような題を付ける |
| 終わり方 | 「〜しましょうか」と申し出る | 新しい示唆か次の操作を1つ書いて終える |

## 向いている人

- 技術的な質問の答えを、そのまま判断や作業に使いたい人
- 回答の長さよりも、聞き返さずに済むことを重視する人
- 「〜が効く」「〜を支える」のような比喩より、何がどう変わるかを知りたい人
- AIが書いた日本語に特有の読点の多さや翻訳調が気になる人
- PR概要欄、commit message、設計文書を、後から別の人が読んでも誤読しない形で書かせたい人
- 根拠の確かさを、文の言い方ではなく明示的な記述で知りたい人

## 向いていない人

- 短い答えを好む人。このプロンプトは既定の簡潔さより網羅を優先するため、回答は長くなりやすい。長さを指定したときは指定に従う
- 柔らかい会話調の答えを好む人。比喩や言い換えを使わないため、文は硬く、説明的になる
- 補足を丸括弧で書く文体や、ダッシュを使う文体を好む人
- 和文と英字の間に半角空白を入れる表記を好む人
- 読点を多めに打つ文体を好む人。このプロンプトは、人間が書いた技術文書と同じ程度まで読点を減らす
- 小説、エッセイ、広告文のように、比喩やリズムが価値になる文章を書かせたい人。これらは適用範囲外にしているが、境界の判断はモデルに任されている

## 好みが分かれる点

次の規則は、合わない人が多いと考えられる規則です。合わないときは、その規則を消すか書き換えて使えます。

- 規則3、丸括弧とダッシュの禁止。略語の補足も「大規模言語モデル、略してLLM」のように文中で書く
- 規則4、和文と英字の間の空白の禁止
- 規則8、比喩の禁止。比喩は、読み手が例えを求めたときだけ「〜に例えると」と明示して使う
- 規則12、読点の制限。短い主題の「は」の後には読点を打たない
- 情報量の節、簡潔さより網羅を優先する方針。判断を変えない項目は書かせないが、それでも回答は長くなる
- 情報量の節、「私は〇〇を確認できていない」と一人称で書く方針。後から読まれる文章では規則11により「未確認:」の項目にする
- 規則2、太字の扱い。重要性の強調には使わず、書名や項目名を見つけやすくするためにだけ使う

## 使い方

`system-prompt.md` の本文を、Claudeの個人設定、プロジェクトの指示、APIのsystemプロンプトのいずれかに貼ります。3つの節は独立しているので、`<writing_rules>` だけを使うこともできます。プロンプトの規則同士は番号で参照し合っているため、規則を消すときは参照している箇所も直してください。規則8と規則11は、情報量の節から参照されています。

## 根拠と検証

各規則は、論文、公的な文書、技術文書の慣行と、生成した出力の測定を根拠にしています。主なものは次のとおりです。

- 比喩と無生物の主語: Clark他2026は、14のLLMが無生物の主語に動作を表す動詞を組み合わせる文を人間より多く使うと報告している。対象は英語である。
- 読点: 本多勝一『**日本語の作文技術**』の原則、石崎2005の音読のポーズの分析、textlintの日本語技術文書向けルール集の「1文の読点は3つまで」をもとにした。
- 情報の順序: Clark と Haviland 1977、Ferreira と Yoshita 2003、Imamura他2016は、旧情報を先に置くと理解が速いか、話し手が旧情報を先に置くと報告している。後の2つは日本語の実験である。
- 文の長さと箇条書き: 文化庁の建議「公用文作成の考え方」は、1文が50〜60字を超えたら見直すこと、並列する項目が3つ以上なら箇条書きにすることを挙げている。

読点の規則は、生成した出力で効果を測りました。

表3 人間が書いた技術文書と、規則12を入れる前と後の出力の読点の密度。出力は同じ5件の依頼への回答

| 文章 | 読点1つあたりの字数 | 「は」の直後に読点を打つ割合 |
| --- | --- | --- |
| 人間が書いた技術書 js-primer | 44.9 | 32% |
| 規則12を入れる前の出力 | 25.5 | 69% |
| 規則12を入れた後の出力 | 44.9 | 25% |

この測定には限界があります。生成は依頼ごとに1回か2回で、使ったモデルは1種類です。規則12を入れた版では、プロンプト自身の読点も同時に減らしたため、2つの変更の効果を分けて測っていません。他の規則も、少数の生成で副作用がないことを確かめた程度です。

## 注意

- このリポジトリは個人のプロンプトを公開するものです。Anthropicの公式のものではありません。
